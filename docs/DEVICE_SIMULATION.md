# Vest simulation (Wokwi) → OrbitCare

> **Currently OFF** (`DEVICE_INPUT=off`, the default). The team decided OrbitCare's live data stays the
> PhysioNet BIDMC recordings (real patient measurements). Everything below applies only after setting
> `DEVICE_INPUT=on` in `.env`.

The OrbitCare vest is simulated on Wokwi (ESP32) until the real sensors exist. The simulation sends one
reading every 5 seconds to OrbitCare, which treats it exactly like real data — the same validation,
analysis, alerts, crew alarm and crew chat — but labels it everywhere as **simulated values**.

## What OrbitCare does with each field

| Firmware field | In OrbitCare |
|---|---|
| `heart_rate_bpm`, `spo2_percent`, `respiratory_rate_bpm` | Validated (physically possible limits), analysed with the documented thresholds, alerts and crew alarm |
| `bp_systolic_mmhg`, `bp_diastolic_mmhg`, `skin_temperature_c`, `activity`, `motion_index`, `co2_ppm`, `radiation_index` | Stored exactly as sent (`device_readings.payload`), **not analysed** — no sourced limits yet; CO2/radiation are generated by the firmware |
| `client_reading_id` | Required; a retried POST with the same ID is not stored twice |
| `astronaut_id` | Optional; if present it must be the code of the astronaut the device is registered to |
| `timestamp` | Kept as the device's clock. A reading more than 30 s old (sent from the offline queue) is stored but not analysed |

The response says what happened: `status` = `analysed` / `late` / `no_vitals` / `duplicate`, plus
`analysed`, `rejected` and `stored_not_analysed` field lists.

Alerts need 10 seconds out of range — with one reading every 5 s that is **2 readings in a row**
(and 2 in-range readings to resolve). Keep `SEND_MS = 5000`; readings that arrive less than 2.5 s apart
(a burst from the queue) are stored but not analysed.

## Setup (on the computer running OrbitCare)

1. Register the device for an astronaut (prints the token once):
   ```
   php cli/register-device.php <astronaut email or astronaut ID> orbitcare_vest_01 simulated
   ```
   From its first reading, this stream becomes that astronaut's data source (their recorded replay stops).
2. Start the device gateway — it serves **only** `POST /api/device/readings`, never the rest of XAMPP:
   ```
   php -S 127.0.0.1:8091 cli/device-gateway.php
   ```
3. Give it a public address for Wokwi's cloud: `ngrok http 8091`.
   Never point ngrok at Apache (port 80): XAMPP's phpMyAdmin would become reachable from the internet.

Onboard a spacecraft none of this is needed: the vest talks to the onboard OrbitCare server over the
local network, without internet.

## Firmware changes (sketch.ino)

```cpp
const char* SERVER_URL   = "https://<ngrok-address>/api/device/readings";
const char* DEVICE_ID    = "orbitcare_vest_01";          // as registered
const char* DEVICE_TOKEN = "<token from register-device>";
const char* ASTRONAUT_ID = "<astronaut ID printed by register-device>";

// Knob ranges that reach OrbitCare's warning AND critical zones (simulation only):
v.hr   = readPot(PIN_HR,   30, 180);
v.spo2 = constrain(readPot(PIN_SPO2, 80, 100), 0, 100);   // critical is below 90 %
v.rr   = readPot(PIN_RR,    4,  40);
```

- Keep `SEND_MS = 5000` and `data_source = "wokwi_simulated"`.
- The Wokwi project link is public: anyone who opens it sees the token. Make the project private or
  revoke the token after the event: `php cli/register-device.php --revoke orbitcare_vest_01`.

## Demo scenario

Turn the SpO2 knob below 90 % for ~10 s → red LED on the vest → critical alert in OrbitCare → the crew
hears the alarm and sees the emergency card → someone presses *On my way* → turn the knob back above
95 % for ~10 s → the alert resolves and a recovery card appears in the crew chat.
